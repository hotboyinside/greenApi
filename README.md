# GREEN API

React-приложение для отправки и получения текстовых сообщений в MAX через GREEN-API.

Проект находится в разработке.

Доступны подключение к инстансу MAX, проверка его состояния, создание локальных
чатов по номеру получателя, отправка текстовых сообщений и выход из сессии.
Получение сообщений будет добавлено следующим этапом. Чаты и сообщения хранятся
в памяти текущей сессии.

## Стек

React, TypeScript, Vite, CSS Modules, React Hook Form, Yup, Vitest, ESLint и Prettier.

## Требования

- Node.js 24.
- pnpm — версия указана в поле `packageManager` в `package.json`.

## Локальный запуск

Установить зависимости:

```powershell
pnpm install
```

Создать локальный файл настроек:

```powershell
Copy-Item .env.example .env.local
```

В `.env.local` указать `VITE_GREEN_API_URL` — значение `apiUrl` из настроек
инстанса в личном кабинете GREEN-API. Адрес в примере нужно сверить со своим
инстансом. Не добавлять к нему путь метода, `idInstance` или токен.

Запустить сервер разработки:

```powershell
pnpm dev
```

Открыть адрес, который появится в терминале.

## Переменные окружения

| Переменная           | Назначение                           |
| -------------------- | ------------------------------------ |
| `VITE_GREEN_API_URL` | Базовый адрес GREEN-API для запросов |

Vite предоставляет значение в коде через `import.meta.env.VITE_GREEN_API_URL`.
Все переменные с префиксом `VITE_` доступны в браузере и подставляются при сборке,
поэтому `apiTokenInstance` в них не храним. Учётные данные пользователь
вводит в интерфейсе приложения.

После изменения `.env.local` нужно перезапустить сервер разработки. Для изменения
настроек опубликованного приложения нужно собрать его заново. Файл `.env.example`
хранится в Git, локальные `.env`-файлы исключены.

При подключении приложение проверяет наличие адреса, а API-клиент — его формат.
Инстанс должен быть заранее авторизован в MAX через личный кабинет GREEN-API.
После успешной проверки `authorized` открывается экран чатов. Другие состояния
и ошибки отображаются в форме подключения. Выход очищает сессию; после обновления
страницы учётные данные нужно ввести заново. Приложение хранит их только в памяти,
не записывая в `localStorage`, `sessionStorage` или cookies. Список чатов также
хранится в памяти и при обновлении очищается.

## Проверки

```powershell
pnpm lint
pnpm typecheck
pnpm format:check
pnpm test:run
```

ESLint использует `recommendedTypeChecked` и `projectService` для проверок с учётом типов. Команда `typecheck` проверяет обе конфигурации TypeScript без сборки приложения.

Тесты API выполняются в Node.js, тесты интерфейса — в jsdom с React Testing
Library. `vitest.config.ts` отключает загрузку env-файлов пользователя; сетевые
запросы подменяются, реальные учётные данные не требуются.

## Дополнительные команды

- `pnpm format` — форматирование файлов.
- `pnpm test` — тесты в режиме наблюдения.
- `pnpm build` — проверка типов и сборка в `dist`.
- `pnpm preview` — локальный просмотр готовой сборки после `pnpm build`.

Настройки Prettier находятся в `.prettierrc.json`, исключения — в `.prettierignore`. Конфигурация `eslint-config-prettier` отключает конфликтующие правила ESLint.

## Формы и валидация

Формы используют React Hook Form и схемы Yup через `@hookform/resolvers`.
Схема подключения находится в `src/features/connection/connectionSchema.ts`;
тип данных формы выводится из схемы через `InferType`.

Поля обязательны, `idInstance` содержит только цифры. Пробелы по краям
учётных данных удаляются перед отправкой. Валидация выполняется при отправке,
после первой ошибки — при изменении поля. Первое неверное поле получает фокус,
ошибки полей связаны с вводом через `aria-describedby` и `aria-invalid`.
Ошибки подключения обрабатываются отдельно в `src/features/connection/hooks/useConnection.ts`.

Компоненты чата находятся в отдельных папках `ChatScreen`, `NewChatForm` и
`Conversation` внутри `src/features/chat`. Стили, схемы и тесты лежат рядом
с соответствующим компонентом. Общий тип чата вынесен в `src/features/chat/types.ts`.

## Цвета интерфейса

Цвета организованы по схеме: примитивы → семантические токены → компоненты.
Значения палитры определены только в `src/styles/primitives.css`.
В `src/styles/tokens.css` они связаны с назначением: фон, текст, границы,
действия и состояния. Компоненты используют только токены `--color-*`;
прямые значения цветов и ссылки на `--palette-*` в стилях компонентов не добавляем.
Токены подключены глобально через `src/index.css`.

## API-клиент

Метод `sendMessage({ chatId, message }, { signal })` отправляет текст и возвращает
`idMessage`. Yup проверяет непустой текст и ограничение 4000 символов, сохраняя
пробелы и переносы строк. После успешного ответа в переписке отображается текст
сообщения без статуса доставки. При ошибке
текст остаётся в поле. Автоматических повторов нет; потеря ответа не означает,
что сообщение не было принято сервером. Черновики и переписки сохраняются при
переключении между чатами в пределах текущего подключения.

`createApiClient` из `src/shared/api` создаёт клиент для одной сессии.
Ему передаются базовый адрес API, `idInstance` и `apiTokenInstance`.
Форма подключения передаёт адрес из настроек окружения.

Метод `getStateInstance({ signal })` выполняет GET-запрос и возвращает
`{ stateInstance }`. Параметр `signal` необязателен. Поддерживаются состояния
`authorized`, `notAuthorized`, `starting`, `blocked`, `suspended` и
`pendingPassword`. Неавторизованное состояние возвращается как результат,
а некорректная структура или неизвестное состояние — как `invalid-response`.

Метод `checkAccount(phoneNumber, { signal })` проверяет наличие аккаунта MAX
и возвращает `exist`, `chatId` и `fromCache`. Номер передаётся числом в международном
формате: РФ — `7` и ещё 10 цифр, Беларусь — `375` и ещё 9 цифр. Форматирование
пользовательского ввода проверяется схемой Yup в форме создания чата;
пробелы по краям удаляются, номер вводится без плюса и разделителей.
При `exist: false` идентификатор чата пуст; это результат проверки, а не ошибка.
Используется стандартный кэш GREEN-API, автоматических повторов нет.

При наличии аккаунта форма открывает чат с `chatId` из ответа сервера.
Повторное создание выбирает существующий чат без дубликата. Если аккаунта нет,
форма показывает сообщение и сохраняет введённый номер. Выход отменяет
незавершённую проверку и очищает список чатов.

Общий `request` находится во внутреннем транспортном модуле и не экспортируется
через публичный интерфейс клиента. Данные JSON сначала имеют тип `unknown` и
становятся типизированными только после проверки.

Таймаут по умолчанию — 15 секунд, его можно задать через `timeoutMs` при создании
клиента. Отдельный запрос отменяется через `signal`, все запросы сессии —
через `dispose()`. После `dispose()` клиент больше не выполняет запросы.
При новом подключении создаётся новый клиент; приложение хранит один активный
экземпляр. Автоматических повторов запросов нет.

Ошибки представлены классом `ApiError` с кодом `configuration`, `http`,
`network`, `invalid-response`, `api`, `timeout` или `aborted`.
Для HTTP-ошибок доступен `status`. Токен, URL запроса и тело ответа в ошибки
не включаются.
